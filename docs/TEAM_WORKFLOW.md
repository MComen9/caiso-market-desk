# 团队使用与协作流程

## 1. 三类入口

| 我想做什么 | 应使用的入口 | 是否需要开发环境 |
| --- | --- | --- |
| 查看市场、预测与模拟结果 | 项目网站 | 不需要 |
| 下载数据和报告 | 网站数据中心或对应 GitHub Release | 不需要 |
| 复现算法、改代码、提交改进 | GitHub 仓库或配置好的 Codex Cloud 环境 | 需要 |

实际网站、仓库及发行链接以根 README 的已验证地址为准。迁移过程中出现的仓库名或 URL 模板只是目标配置。

## 2. 浏览与下载

打开页面后，先确认数据截止时间、预测目标日和模型版本，再选择枢纽、日期和指标。当前平台包含历史快照；默认展示不代表数据已自动更新。

下载时优先选择与页面同一版本的数据和说明。若需要复现，下载相应输入、脚本、参数与报告，不要只拿一张图或单个预测 CSV 判断训练过程。

出现无法访问、下载不完整或数值不一致时，记录 URL、发生时间、使用的版本和具体表现。报告问题时不要附上账号凭据、浏览器 Cookie 或不相关的内部资料。

## 3. 团队角色

| 角色 | 主要责任 |
| --- | --- |
| 项目维护者 | 维护仓库设置、审核合并、发布版本、确认交接记录 |
| 研究与算法人员 | 定义实验、保证时间划分与输入口径、报告基线和限制 |
| 前后端研发 | 维护模块边界、构建、接口和验证，修复访问及交互问题 |
| 业务与产品人员 | 明确使用场景、解释要求、数据口径和验收标准 |
| 查看者 | 浏览与下载；提出问题和反馈 |

实际成员和权限由仓库维护者配置。本文件不代表已邀请任何成员，也不自动授予修改或发布权限。

## 4. 一次代码或模型改动

1. **说明目标。** 描述使用场景、当前问题、影响范围和可验收结果，先检查现有功能是否已满足。
2. **从明确版本开始。** 使用独立分支，如 `feature/forecast-comparison`、`fix/download-links`、`research/spread-interval-v5`。同一分支不混入无关重构。
3. **实现并验证。** 复用字段和算法；按变化风险执行必要检查。记录真正运行的命令及结果，不以“应该能运行”替代验证。
4. **审阅变更。** 提交说明问题、变化、结果和边界。模型改动附输入版本、时间划分、基线和新旧结果对照。
5. **合并与发行。** 只在相应任务授权范围内合并或发布；生成可追溯的版本及附件清单。
6. **实际验收。** 检查网页显示、数据下载及团队访问；遇到失败保留上次有效版本，并明确当前状态。

发布不等于重训，重训也不等于发布。代码提交、模型结果和面向团队的网站版本应分别有清晰记录，并在发行时建立对应关系。

## 5. 数据与研究结果的发行

### 发行说明至少包含

| 内容 | 要求 |
| --- | --- |
| 代码版本 | 对应提交 SHA 或标签 |
| 数据范围 | 开始/结束时间、市场、枢纽、时区和粒度 |
| 数据来源 | 原始来源、采集时间及质量限制 |
| 模型与结果 | 模型版本、预测生成时间、目标日期和评估窗口 |
| 附件 | 文件名、用途、大小与校验值 |
| 变化 | 本次新增、修复或替换的内容 |
| 未完成事项 | 未通过的检查、未接入的数据或未配置的环境 |

网站所需的小型快照与完整下载包应绑定到同一发行说明。较大历史资料适合放 Releases，不能依赖短期 Actions 产物作为团队唯一的长期下载入口。

### 冻结版本规则

- V1—V4 已有证据、参数、报告和结果保持原版本可追溯。
- 追加实际值时，另建事后评估结果，引用原预测；不改写预测发布时未知的实际字段。
- 修改数据清洗或修复错误时，保留原版本并说明影响，不用新文件悄悄覆盖旧结论。
- 对公开整理或删节的包使用明确名称与清单，避免与原始完整证据包混淆。
- 新版本不能只报告有利指标，应同时给出样本量、基线、误差、方向、覆盖率和模拟假设中与任务相关的内容。

## 6. 在 Codex 中继续开发

源码上传完成后，需要创建并发布 Codex Cloud 环境；选择仓库和保存配置本身不代表准备完成。环境默认安装公开前端，使用 Python 标准库核验冻结 V4；研究训练依赖和完整工作台按需准备。

默认环境准备命令为 `bash scripts/codex-setup.sh`。研究任务需要训练依赖时加 `--research`，工作台开发时加 `--workbench`。安装选项不自动授权或触发模型重训、数据采集和运行数据库初始化。

首个任务按 `docs/CODEX_HANDOFF.md` 进行迁移核验。只有安装、构建和冻结结果复现通过后，才进入具体优化任务。优化时给出目标和接受标准，例如：

> 在独立分支改进预测对比页：同屏查看三个枢纽的 DA、价差及误差指标，保留现有数据口径和下载。检查桌面与窄屏布局、空数据状态、日期切换以及版本一致性。不要修改模型或生成新预测。

或：

> 基于已归档输入开展一个新的价差区间校准实验，保留 V4 冻结基线。先说明时间划分、可用数据与接受标准，再运行比较。结果标为开发研究；没有真正后续数据时，不宣称独立测试改善。不要采购或等待缺口数据。

Codex 环境权限独立于网站和仓库权限。不要把个人云环境的共享设置当作团队已拥有全部代码、账户或数据服务权限。

## 7. 异常与处理

| 情况 | 处理方式 |
| --- | --- |
| 网页打不开 | 确认实际部署状态，再从团队实际网络验证；保留数据下载入口和故障记录 |
| 构建失败 | 定位锁文件、依赖或源码差异；不通过跳过校验来发布未验证结果 |
| 数据下载失败 | 比对发行附件位置、文件大小与校验值；不得把不存在的链接标为可下载 |
| 外部来源不可用 | 保留最近有效快照并展示截止时间，记录缺口；继续已可实现的研究 |
| 模拟不能复现 | 核对输入、参数、日期、时区及代码版本；先解释差异，不直接修改冻结结果 |
| Codex 找不到仓库 | 核对实际仓库是否创建、GitHub 连接的授权范围和环境选择；不改用无关仓库 |
| Codex 环境未发布 | 完成安装与检查后实际 Publish，再开启新任务验证 |
| 需要多人在线写入 | 先设计身份、任务与实验归属，再配置工作台后端；公开只读网站保持原边界 |

## 8. 发布完成的证据

迁移完成应能提供：实际仓库地址及提交版本、实际网站地址、可下载且完整的数据发行、明确的目录和运行说明，以及 Codex 环境与首任务的真实状态。

如果某一步受连接、登录或权限阻塞，应把已完成的交付与具体阻塞分别写清。不能把“材料已准备好”写成“远端已上线”。
